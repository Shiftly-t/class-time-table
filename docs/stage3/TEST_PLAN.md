## 準備する架空データと測定

- 将来のJST平日DとD+1、通常授業4コマ、非重複の講習コマ、休校/特別開校/模試、講師A/Bを用意。毎週設定・日別例外・欠席・手動授業・未確定/確定/公開予約・QRのみ生徒・done履歴を別々に作る。20人の競合試験はテスト専用QRで行う。
- owner1/admin2/employee2/登録外の独立Auth sessionを使う。親QR20件と職員アカウントを混同しない。架空メールは管理するテスト用ドメイン/予約例示ドメインを使い、実ユーザーへのメール/SMSを送らない。
- ケースごとにrunId、テストproject ID/number、schema/API/Web/rules/index/secret-versionのhash、時刻JST/UTC、role、安定requestId、開始/終了fingerprint、used/teacherLoad集計、サーバー観測、所要時間/read数を私有保管。秘密header、QR token、氏名付き全JSONを公開ログへ出さない。
- 突合せは信頼するowner向け私有runnerで行う。保護者へ台帳全体のread権限を与えて検査しない。各枠used＝台帳wishes数、各講師load＝confirmed数、公開confirmedとb_授業の双方向一致、student表示・上限2・学生重複・QRepochを確認する。手動授業も定員に含める。
- 成立・明確な拒否・結果不明を分ける。応答喪失はreceipt照会で解決し、runnerの自動mutation retryを無効にする。SDK内部のtransaction retryを観測し、二重副作用なしを確認。未解決要求があれば次のケースでデータを消さない。
- 並列試験は実Functions endpointへ別session/接続からbarrierを使って送信。同一processのmock競合だけでは代替しない。20並列後に必要なら別途確認して負荷を増やす。
- 不正カウンター等の故障注入は、承認したテストprojectの専用runId範囲で私有runnerが行う。通常の親/講師権限を緩めない。故障注入用関数を本番へ配備しない。

## 検証時の注意

勤務変更と新配置が競合した場合は成立順序で判断する。新配置のcommitが先なら、その後の勤務変更で既存授業を勝手に消さず要振替として保持する。勤務変更が先なら、新規配置は最新の勤務条件で拒否する。「勤務変更をした瞬間に既存授業が全て消える」を合格条件にしない。

Auth/App Checkの拒否codeはSDK/入口によって異なるため、エラーの分類・実際の無書込・ログを記録する。無認可要求が成功しないことが合格条件で、任意の単一HTTP codeだけを成功証拠にしない。

小規模復元の完全スコープは業務データに限定され、Auth/IAM、immutable監査、receipt、lifecycle、通知等は同じ意味で巻戻さない。復元後の古い通知の扱いは未実装の運用方針で、業務再開ゲートとして解決する。
